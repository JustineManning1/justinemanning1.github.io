The analysis

Problem

Claims cycle time kept rising, driving loss-adjustment expense and complaints. Leadership assumed claims were "just getting more complex."

Approach

Decomposed cycle time into stage durations, found 40% was pre-assignment idle time, and designed severity-based triage with auto-assignment for simple claims.

Decision enabled

Every line’s cycle time drops 25-40% after April’s triage rules — simple claims stopped waiting in the same queue as complex ones. Complexity didn’t change; routing did.

Modeled impact: ~$1.1M/yr in loss-adjustment expense + recovered subrogation

The SQL behind this view

These queries run against the raw CSV in this repo (load it into SQLite or DuckDB). The dashboard's aggregates are what these queries return.

SQL · Cycle time by line, before vs after triageSQLite / DuckDB
SELECT line,
       CASE WHEN open_date >= '2026-04-01'
            THEN 'After triage' ELSE 'Before' END AS period,
       ROUND(AVG(cycle_days), 1) AS avg_cycle_days,
       COUNT(*) AS claims
FROM insurance_claims
GROUP BY line, period
ORDER BY line, period;
SQL · Percentile view proves it’s not outliers (window fn)SQLite / DuckDB
SELECT line,
       PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY cycle_days) AS p50,
       PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY cycle_days) AS p90,
       ROUND(AVG(paid_amount_usd), 0) AS avg_severity
FROM insurance_claims
WHERE open_date >= '2026-04-01'
GROUP BY line;

The Power BI translation

The same model expressed as DAX measures — how this dashboard is built when the delivery target is Power BI instead of the web.

Power BI · Cycle time measureDAX
Avg Cycle Days =
AVERAGE ( Claims[cycle_days] )
Power BI · Post-triage improvementDAX
Cycle Improvement =
VAR Pre =
    CALCULATE ( [Avg Cycle Days],
        Claims[open_date] < DATE ( 2026, 4, 1 ) )
VAR Post =
    CALCULATE ( [Avg Cycle Days],
        Claims[open_date] >= DATE ( 2026, 4, 1 ) )
RETURN DIVIDE ( Pre - Post, Pre )
